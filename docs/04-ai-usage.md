# 04 · AI 辅助使用与个人参与说明

本项目使用了 ChatGPT 和 Codex 辅助需求分析、代码实现与工程检查。以下内容按实际过程记录 AI 的作用和我的参与，不将 AI 生成或修改的代码描述为本人完全独立手写，也不把 Mock 结果当作真实模型验证。

## 1. 需求理解与方案选择

我先阅读并比较了四道项目题：短视频脚本、企业知识问答、内容任务规划和素材审核排期。比较时，我重点考虑了能否在有限时间内完成一个可运行、可测试、可解释的 Agent，而不是只做一个大模型问答演示。

我最终选择企业知识问答 Agent，主要基于以下判断：

- 企业问答可以把模型决策拆成搜索文档、读取原文和提交答案三个明确动作，便于验证真实的动态工具调用。
- 文档 ID 和原文片段可以作为证据，使答案能够追溯，不需要仅凭模型表述判断正确性。
- 文档冲突、知识库无结果、上下文追问和工具失败都可以构造成清晰的验收场景。
- 对校招项目而言，我更希望优先保证“模型选择工具—执行工具—观察结果—模型继续决策”的核心链路可靠，而不是增加无关前端、数据库或复杂 Agent 框架。

在方案讨论和取舍中，我参与确定了 Python、OpenAI 兼容 Chat Completions Function Calling、DeepSeek 官方 API、本地合成 JSON 知识库和 CLI 的实现方向。检索和引用校验保持在本地确定性代码中，下一步动作交给模型选择，以区分工程保护机制与模型自主决策。

## 2. AI 工具使用情况

### ChatGPT

ChatGPT 主要用于前期需求拆解、技术方案比较和项目初稿生成。初稿包括合成制度数据、Agent 循环、工具定义、离线 Mock、测试示例、README 和文档框架。ChatGPT 也提供了测试场景和交付检查建议。这些内容为项目提供了起点，但不能代替我对方案的选择、真实 API 接入和最终结果验证。

### Codex

Codex 主要用于在当前工作区内进行工程化检查和修改，包括：

- 阅读 `README.md`、核心源码、测试、样例和交付文档，检查真实模型循环是否存在硬编码动作。
- 创建并检查 `.venv`，安装依赖，运行离线测试和样例生成。
- 补充搜索后才能读取、原文引用校验、冲突候选完整读取、调用上限、敏感信息脱敏和完整 Trace 等保护机制。
- 根据 DeepSeek 官方接口要求，为 `deepseek-flash` 增加非思考模式参数，避免 `tool_choice="required"` 在思考模式下产生 400 错误。
- 分析真实测试失败 Trace，定位同一模型回合返回多个工具调用时的适配问题，并辅助完成代码修复和回归测试。
- 对七条最终真实 Trace 做引用、冲突、失败恢复、字段完整性和敏感信息检查，并整理 README 与交付文档。

Codex 完成了上述代码检查和具体工程修改；我没有把这些修改描述为本人完全独立手写。

## 3. 我的实际参与过程

我负责了选题确认、方案取舍、真实环境配置、测试执行、问题反馈、修复结果验证和最终交付决策。

我在 Windows 和 VS Code 环境中运行项目，使用 PowerShell 配置 DeepSeek API 所需环境变量。实际 Key 只保存在本地运行环境，没有写入源码、Trace 或文档。配置形式如下，示例不包含真实密钥：

```powershell
$env:OPENAI_API_KEY="<本地 DeepSeek API Key>"
$env:OPENAI_MODEL="deepseek-flash"
$env:OPENAI_BASE_URL="https://api.deepseek.com"
```

我实际参与或完成的操作包括：

1. 检查 DeepSeek API 是否可以连接，并确认模型名称和 Base URL 与项目的 OpenAI 兼容调用方式一致。
2. 运行 Python 单元测试，确认离线工具、引用校验、冲突保护和边界逻辑能够通过。
3. 运行七组真实模型用例以及验收脚本，根据终端输出检查每个场景的状态和失败原因。
4. 首轮真实验收发现只有 4/7 通过后，整理失败场景 02-conflict、04-paraphrase、06-search-failure 及其错误信息，交给 Codex 做针对性分析。
5. 在修复方案上，我确认不能为了通过测试把冲突答案或失败重试写成固定 if/else；修复必须保留模型收到观察后再选择下一动作的过程。
6. 修复完成后，我只重新运行三个失败场景，没有重复执行已经通过的四个场景，以减少不必要的 Token 消耗。
7. 最后再次运行验收脚本，确认七组场景全部通过，并根据输出确认动态路径已经成立。

用于定向复测的命令为：

```powershell
.\.venv\Scripts\python.exe -m examples.run_live_cases `
  --case 02-conflict `
  --case 04-paraphrase `
  --case 06-search-failure

.\.venv\Scripts\python.exe -m examples.live_evaluation_check
```

## 4. 真实问题分析与修复验证

首次真实测试中，明确答案、资料外问题、上下文追问和读取失败场景通过，但 02、04、06 返回 `incomplete`。从 Trace 和错误输出可以看到，API 已经成功响应，失败也不是关键词检索本身造成的；真正的问题是 DeepSeek 可能在一个响应中提出多个工具调用，而当时的模型适配层把这种响应直接视为错误并终止 Agent。

我先根据终端结果判断应该优先处理真实执行器兼容问题，而不是修改验收预期或硬编码三个场景。随后我把失败列表和 Trace 提供给 Codex。Codex 辅助修改了模型适配与执行器逻辑：保留模型提出的多个调用，但不提前执行这些尚未观察结果的动作，而是把“每轮只能选择一个工具”的协议反馈返回给模型，让模型下一轮重新选择单个动作。同时，冲突保护会要求模型在使用一个冲突候选前读取同主题的其他候选。

我通过定向复测验证了修改结果：

- 02 最终读取 D01 和 D02，分别引用 30 个自然日和 15 个自然日的原文，以 `needs_clarification` 结束，没有自行判断新版本优先。
- 04 能把“刚入职的新人要领笔记本”改写为与新员工设备申领相关的检索词，并引用 D03。
- 06 第一次搜索观察到模拟连接失败后，模型下一轮再次选择 `search_documents`，而不是由执行器自动重试。

这次过程让我确认，真实模型验收不能被 Mock 记录替代；适配层是否正确处理模型响应格式，会直接决定 Agent 循环是否真正成立。

## 5. 最终验证结果

- 离线单元测试：26/26 PASS。
- DeepSeek 真实 LLM 验收：7/7 PASS。
- 自动验收脚本：PASS。
- 动态决策路径：成功搜索后选择 `read_document`；失败搜索后模型重新选择 `search_documents`。
- 最终七条 Trace 报告 Token：prompt 23,919，completion 2,624，总计 26,543。
- 七组真实输入、输出和 Trace 保存在 `examples/live/`。

最终引用和事实核验由 Codex 辅助完成，并通过验收脚本与人工逐条检查相互印证。我没有将其描述为完全未经 AI 辅助的独立审查。人工检查确认引用均来自对应文档原文，02 完整披露冲突，06 能证明模型在观察失败后改变后续动作。03 中“制度类知识库通常不收录”属于模型的概括性措辞，不是公司制度事实，但不影响两次检索为空所支持的 `not_found` 结论。
