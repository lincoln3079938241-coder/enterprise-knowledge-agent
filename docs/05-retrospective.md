# 05 · 项目复盘

## 1. 项目目标与我的方案选择

这个项目的目标不是做一个能够流畅回答问题的聊天机器人，而是实现一个可验证的企业知识问答 Agent：模型需要根据用户问题选择工具，工具执行后把观察结果返回给模型，再由模型决定下一步动作或结束。

我在比较四道项目题后选择企业知识问答，是因为它能把 Agent 的动态决策和可靠性要求展示得比较完整。搜索、读取和提交答案三个动作边界清楚；文档 ID 与原文引用可以验证答案；冲突、缺资料和工具失败也能形成明确的测试条件。我参与确定了 Python、OpenAI 兼容 Function Calling、DeepSeek、本地 JSON 知识库和 CLI 的路线，没有引入前端、数据库或复杂 Agent 框架，把时间集中在核心循环和证据约束上。

## 2. 实际开发与验证过程

项目初稿由 ChatGPT 辅助生成，Codex 在本地工作区完成了较多代码检查和工程修改。我主要负责理解需求、确认方案、配置真实 API、执行测试、反馈错误和验证修复结果。

我在 Windows 和 VS Code 中使用项目运行环境，通过 PowerShell 设置 DeepSeek API Key、`deepseek-flash` 模型名称和官方 Base URL。密钥只进入本地环境变量，没有写进源码。之后我分别执行离线单元测试、七组真实模型测试和验收脚本，并根据终端输出检查每个场景的状态。

离线测试能够很快验证工具、引用和边界逻辑，但我没有把离线 Mock 的成功当作最终结论。真正接入 DeepSeek 后，首轮结果只有 4/7，通过真实 Trace 才发现执行器对模型响应格式的假设不够稳健。修复后我只重跑 02、04、06 三个失败场景，最终达到离线 26/26、真实模型 7/7 和自动检查 PASS。

## 3. 遇到的最困难问题

最困难的问题不是编写搜索函数，而是判断失败究竟发生在哪一层。首轮失败的三个场景表面上都是 `incomplete`，但原因并不相同于“模型不知道答案”或“知识库检索不到”。02 已经成功搜索到 D01、D02 和 D07，04、06 甚至还没有进入工具执行；错误信息指向模型适配层对多个工具调用的处理。

这个问题让我意识到，只看最终状态不够。需要结合 Trace 中的模型步骤、工具参数、工具结果和下一动作，区分以下几类问题：

- API 请求是否失败；
- 模型是否选择了错误动作；
- 工具本身是否执行失败；
- 适配层是否错误解析了模型响应；
- 执行器的安全规则是否拒绝了不合格答案。

这次实际故障属于适配层和执行器兼容问题，而不是 DeepSeek API 连接失败或知识库内容不足。

## 4. 多工具调用兼容问题的定位与解决

DeepSeek 可能在单次响应中提出多个函数调用。原实现为了保持 Trace 简单，假设每轮只会收到一个调用，一旦发现多个调用就直接抛出异常。这使 Agent 在真正观察工具结果之前结束，因此 02 无法继续读取两份冲突制度，04 和 06 也没有进入正常检索流程。

我查看失败结果后，将三个场景和错误日志反馈给 Codex，并明确修复不能变成“遇到 06 就自动重试”或“遇到 02 就固定读取 D01、D02”。Codex 辅助完成的修复是：

1. 模型适配层不再丢弃多个工具调用。
2. 执行器不直接执行同一轮预排的多个动作，因为后一个动作并没有观察前一个动作的结果。
3. 执行器为这些调用返回单步协议反馈，让模型在下一轮重新选择一个工具。
4. 冲突校验在模型读取一个冲突候选后，要求继续查证同主题的其他候选，避免只引用单边证据。

修复后，02 按顺序读取 D01 和 D02；06 在看到第一次搜索的 `ConnectionError` 后，由模型再次选择搜索。这种处理既增强了兼容性，也没有把业务动作写死在执行器里。

## 5. Agent 动态决策与普通 Workflow 的区别

我对 Agent 最重要的认识是：核心并不是调用大模型生成一段答案，而是让模型依据外部观察动态选择下一步动作。

普通 Workflow 可以预先规定“先搜索、再读取、最后回答”，但它无法证明模型真的根据结果改变行为。本项目最终保留了两条可比较的真实路径：

- 搜索成功并返回相关文档时，模型下一步选择 `read_document`。
- 搜索返回临时连接错误时，模型观察错误后再次选择 `search_documents`。

这两个路径的差异来自工具观察，而不是执行器中的固定分支。执行器负责预算、协议和证据安全；模型负责在允许范围内决定业务动作。我认为这两部分缺一不可：完全放任模型会降低可靠性，全部写死又会退化成普通 Workflow。

## 6. 文档证据约束与冲突处理

搜索结果只提供文档 ID、标题和摘要，不等于可信答案。模型必须调用 `read_document` 获取原文，最终引用也必须是已读取原文的真实子串。这样可以避免模型依据摘要扩写，或者引用一个实际没有读取的文档。

D01 和 D02 是最能体现证据约束的场景。两份制度分别规定差旅行程结束后 30 个自然日和 15 个自然日提交报销，但都没有说明适用范围或优先级。即使 D02 版本号和日期更新，也不能据此推断它必然覆盖 D01。最终回答必须列出两份原文并返回 `needs_clarification`，要求确认适用制度，而不是擅自选一个数字。

执行器中的引用和冲突校验是确定性的工程保护，但它不能代替完整的语义事实核验。当前实现能够验证引用是否为原文子串、冲突候选是否完整读取，却不能自动判断回答中的每个自然语言推论是否都严格受引用支持。

## 7. 工具异常与执行上限设计

工具失败不应该被吞掉，也不应该由执行器无条件重试。失败结果会作为 `tool` 消息进入模型上下文，模型可以根据错误类型、已有证据和剩余预算决定重试、换查询、选择其他工具或以 `tool_error` 结束。

06 和 07 分别注入一次搜索失败和读取失败。最终真实 Trace 显示 DeepSeek 都在观察错误后选择有限重试，而不是执行器自动推进。与此同时，`max_steps` 和 `max_tool_calls` 会在模型反复调用或无法结束时返回明确的 `incomplete`，避免无限循环和虚假完成。结构化提交同样计入工具预算。

## 8. 测试结果与仍然存在的限制

最终结果为：

- 离线单元测试 26/26 PASS；
- DeepSeek 真实 LLM 验收 7/7 PASS；
- 动态路径检查 PASS；
- 最终七条 Trace 报告 prompt 23,919、completion 2,624，总计 26,543 Token。

Mock 测试和真实模型测试在项目中明确分开。Mock 适合稳定验证执行器边界，但不能证明真实模型会按预期选择工具；这也是为什么首轮离线测试通过后，真实模型仍暴露出多工具调用兼容问题。

当前仍有以下限制：

1. 检索采用关键词和同义词归一化，面对词面差异更大的问题可能漏检。
2. 引用校验是原文子串检查，不是完整的语义蕴含验证。
3. 冲突识别依赖合成数据中的 `topic` 和 `claim_value` 字段，真实企业文档需要更复杂的权威性、适用范围和生效关系建模。
4. 当前只适配 Chat Completions Function Calling，Responses-only 服务需要单独适配。
5. 真实模型行为具有随机性；模型、提示词或知识库变化后仍需重新验收。
6. 03 的回答包含“制度类知识库通常不收录”这一概括性措辞，它不影响 `not_found` 结论，但说明回答层面仍需要更严格的语义约束。

## 9. 下一步优化方向

如果继续完善，我会优先考虑：

- 为检索增加更系统的中文查询改写评测，必要时再引入 Embedding，而不是先增加框架复杂度。
- 增加回答与引用之间的语义一致性检查，减少“引用正确但解释扩展过度”的风险。
- 在文档元数据中明确制度权威级别、适用部门、生效和废止关系，使冲突处理更接近真实企业场景。
- 增加多轮上下文、不同模型和重复运行的稳定性评测。
- 对真实 API 用量和失败响应建立更完整的运行清单，便于成本和回归追踪。

这些内容是后续方向，不属于本次已经完成的功能。

## 10. 个人总结

通过这个项目，我对 Agent 工程的理解从“让大模型会调用工具”进一步变成了“让模型决策、工具观察和工程保护形成可验证的闭环”。真正影响可靠性的往往不是最终回答是否流畅，而是模型是否读取了证据、错误是否进入上下文、冲突是否被保留、执行器是否能处理真实模型返回的意外格式，以及每一步是否可以通过 Trace 复核。

我在本项目中的主要贡献不是独立手写全部代码，而是完成选题和方案取舍、搭建真实 API 运行环境、执行验收、识别和反馈失败、判断修复不能破坏动态决策、定向回归并确认最终交付结果。ChatGPT 和 Codex 提供了方案、代码和工程修改支持，我则需要对测试结果、技术边界和最终提交负责。这次过程让我更清楚地认识到，Agent 的自主性必须和确定性的安全约束、可观察性及真实模型验证一起设计。
